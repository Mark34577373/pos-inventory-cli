# Days 20–21: business preferences and analytics

## Store settings (Day 20)

Sign in, open Settings, and save one section at a time. Settings belong to the
server-authorized store. Each save uses a revision number to prevent lost updates;
reload after saving in another window. Ownership fields cannot be submitted.
Public demo and read-only deployments cannot save preferences.

Business contact details and descriptions are optional. Receipt preferences are
plain text, escaped by Jinja. The preview shows saved preferences and creates no
transaction. New sales snapshot receipt details and category attribution inside
the same transaction as stock deduction. Earlier receipts explicitly disclose
that their original business profile was not recorded. Historical category
snapshots remain NULL: migration never guesses categories from today's products.

Tax is a store-specific integer number of millionths of the subtotal (default
82500 = 8.25%). Input accepts 0–100 percent with up to four decimal places.
Checkout uses Decimal and rounds half up once to integer cents on the subtotal.
The authoritative rate is read after BEGIN IMMEDIATE. A stale total is rejected;
no stock or sale is committed. Completed sales retain their recorded rate and
amounts; refund allocation continues using the original sale's tax. Store owners
are responsible for legally appropriate rates. This is not a jurisdictional tax
compliance engine. USD is the only supported currency. Business timezone remains
the deployment's TCCP_TIMEZONE; changing timezone after recording sales is unsafe
because historical sales use local wall-clock timestamps.

Blank per-product stock thresholds inherit the store default (initially 5).
Explicit product overrides win, including zero. Changing the default never changes
stock, overrides or adjustment history. Zero stock is always out of stock.
Dashboard stock-alert and recent-transaction panels can be hidden independently;
reporting defaults do not alter accounting records.

Account settings expose existing identity, membership and logout capabilities.
Password change, recovery, email verification and MFA remain unsupported.

## Safe migration

Back up SQLite using its backup API or the existing maintenance backup command;
retain the original file and verify the backup before upgrading. With writers
stopped, use `python manage.py init` for the existing migration command.
Migration 20 adds store_settings, receipt_snapshot and category snapshot columns.
It creates one default settings record per existing store and a trigger for new
stores, with foreign-key and validation constraints. It never rewrites old sales,
refunds, line items or stock history. Initialization is transactional and
idempotent. Production startup requires the current schema; it never migrates
implicitly. Test a disposable backup first. For recovery, restore the verified
pre-upgrade backup with the matching application version; do not drop columns or
reset a live database. The local desktop continues to use legacy store 1.

## Advanced analytics (Day 21)

The existing analytics service still owns one bounded SQLite read transaction.
`analytics_details.py` projects additional views inside that same transaction;
it is not an independent reporting implementation. There is no report cache. Advanced analytics queries run only when rendering or
exporting reports.

### Accounting and filters

- Gross sales: persisted sale total including tax, on sale business date.
- Refunds: persisted completed refund totals including allocated tax, on the
  persisted refund business date, even when the original sale is outside the range.
- Net sales: gross minus refunds; not profit.
- Transaction count: matching committed original sales, not refund events.
- Average transaction value: gross divided by transaction count, half-up rounded
  to a cent; zero when no sales.
- Merchandise revenue/units: original line prices/quantities; product and category
  figures exclude tax. Merchandise refunds subtract the original allocated tax.
- Verified tax collected: only sale differences reconciled to their recorded rate;
  unverified legacy differences remain separately disclosed. Refunded tax uses
  the immutable refund allocation. No new allocation policy was introduced.
- Sale-cohort refund rate: all recorded refunded units of the original lines sold
  in the selected period divided by units sold in that period. N/A without original
  units; later refunds may change this rate. This avoids dividing refund-date
  movements from older sales by unrelated current-period units.

Product and historical-category filters select **whole baskets containing a
matching historical line**. Combined filters must match the same original line;
payment filters refer to the original payment method. Gross, tax, average, charts,
rankings, refunds, comparisons and all CSVs use the identical basket cohort.
Co-sold products remain included; these filters are not tax-apportioned line-item
reports. Foreign product/category IDs fail with a generic unavailable-filter error.
Category filters never use today's product assignments for historical sales.
Missing snapshots are Unknown; recorded uncategorized sales are separate. Current
category options and any selected deleted historical category remain available.
Snapshot names, prices and attribution do not change after product edits.

Inventory intelligence is explicitly a **current** active-stock view, not a
historical accounting widget. Product/category selection applies to current
metadata; payment/date selection does not change units on hand. No cost/profit
valuation is fabricated. Existing selling-price-times-stock displays are labeled
as retail selling prices, not acquisition cost.

### Charts, comparisons and forecasts

Hourly is a 24-bin hour-of-day profile across the selected dates. Sales use their
recorded local hour; refund UTC timestamps are converted to TCCP_TIMEZONE for the
hour, with eligibility still governed by persisted business_date. Repeated DST
hours combine because original sale timestamps contain no UTC offset. Daily,
Monday-based weekly and monthly buckets retain inclusive date ranges; boundary
buckets may be partial. Gross/refund/net charts use one scale and a visible zero
baseline, with negative net extending left. Native tooltips, keyboard selection,
live descriptions and tables supplement colors. Category/product trends list
recorded movements; absent rows are not invented history.

Today compares to yesterday. This calendar week includes Monday–Sunday and
compares to the previous Monday–Sunday; unelapsed days can be zero. This calendar
month compares full calendar months, potentially different lengths. Month-to-date,
custom and other presets compare preceding equal-length calendar periods. Export
links freeze dates **and the comparison model**, so a later download cannot drift
to a different month. Negative/zero baselines yield N/A percentage; absolute change
is always shown and is not colored as a claim of business improvement.

Sales velocity is gross units sold divided by selected calendar days. Estimates
require at least seven complete days, recorded opening history covering the start,
positive demand and no basket/payment restrictions. Days remaining = current units
× period days ÷ units sold, rounded half up to one decimal. Zero demand is not
infinity; it displays N/A. Opening history uses immutable initial audits or migration
baselines. Slow moving means at most one matching unit sold during the selected
period with known opening history; missing history is labeled separately. These
are simple estimates, not replenishment recommendations or predictions.

### Exports and resource limits

Existing summary, periods, top-products, transaction and refund-ledger CSVs remain.
Added exports: `categories`, `performance` (all matching historical products),
`comparisons`, `category-trends` and `product-trends`. Text uses existing spreadsheet
formula neutralization; all monetary output is exact decimal USD from integer
cents. Filenames are fixed-kind/date-based, responses are private/no-store, and
export routes use the same authentication/cohort/limits as the page. Printing uses
the existing external print handler; no server PDF dependency was added.

Limits: 366 days; 10,000 sales and refunds per current/previous period; 50,000
sale/refund lines; 5,000 inventory or historical products. Over-limit reports fail
rather than silently truncate accounting. UI detail tables explicitly show their
100-product/500-trend-row display limits; CSVs contain full bounded results.
Migration 21 adds store-aware product/category cohort indexes and an initial-stock
history covering index. Existing store/time, refund-date and refund-line indexes
remain. The fictional benchmark inserted 1,200 sales and generated a filtered
hourly advanced report in **0.141 seconds** locally; it is not a production SLA.

## Security review and compatibility

Settings GET/POST use the existing default authentication guard and CSRF pipeline.
Service reads/writes derive store ID from authorized server context. Settings
ownership fields are rejected at both HTTP and service boundaries. Changes use
parameterized values, allowlisted columns, BEGIN IMMEDIATE and an expected revision.
Demo and read-only owner writes fail server-side. Advanced filters reject foreign
IDs, and all joins retain store relationships. No secrets, hashes, credentials or
private export files are introduced or logged. Existing cookie/session/host/CSP,
no-store, request-size, error handling and persistent throttle protections remain.
The review included [Flask's security guidance](https://flask.palletsprojects.com/en/stable/web-security/).

The Tkinter/CLI clients remain fixed to trusted local legacy store 1, now using
its configured exact tax and default thresholds. Their completed receipt tax labels
no longer consult a newly changed rate. Web historical receipts render stored
customization; the desktop retains its existing receipt layout. No real payments,
refund rails, currency conversion, timezone migration, recovery or MFA were added.
